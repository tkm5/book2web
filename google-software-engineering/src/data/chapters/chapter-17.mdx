## Code Searchとは何か

Code SearchはGoogleのコードの閲覧と検索のためのツールであり，フロントエンドUIと各種バックエンド要素から構成されている．コードベースの規模に合わせてスケールする必要性から直接生まれてきたツールだ．当初はランキングを備えた社内コード用grepツールと社外公開版のUIを組み合わせたものだったが，時間の経過と共にその機能と役割は大きく進化した．

Kythe（旧称Grok）の統合により，相互参照（クロスリファレンス）とシンボル定義へのジャンプ能力が追加され，Code Searchは単なる検索ツールの枠を超えた鍵となるツールとしての地位が確立された．相互参照の統合前後で，開発者がCode Searchを利用する頻度は劇的に増加し，クロスリファレンスなしの世界は想像し難いものとなった．

統合開発環境（IDE）とは対照的に，Code Searchはスケールする状態でコードを読み，理解し，探索するというユースケース向けに最適化されている．内容の検索と相互参照の解決のためにクラウドベースのバックエンドに依存しており，「コードに関する来るべき質問に1クリックで答える」という原則で開発が進められている．

<KeyConcept title="Code SearchのUI設計">
Code SearchのUIは以下の特徴を備えている．

- 検索ボックスにはファイル，シンボル，ディレクトリーへの素早いナビゲーション用の候補機能がある
- 大半のトークンはクリック可能であり，関数呼び出しは定義へ，インポートされたファイル名は実際のソースへとリンクされる
- Piper（バージョンコントロール）との統合により，ファイルの履歴，変更の著者，バージョン間の差分，blameビューを表示できる
- コマンドラインやRPC APIを通じて他のツールに組み込みが可能であり，これにより自動化されたワークフローへの統合も実現されている
</KeyConcept>

## グーグラーはどのようにCode Searchを使うか

Code Searchの利用目的は，コードに関する質問の答えを得ることである．ユーザー調査によって，その利用は5つのパターンに分類されている．これらの分類は，Code Searchのユーザーインターフェイスの最適化を導く上で極めて有益である．

### どこに（Where）：16%

コードベース内で特定の情報がどこに存在するかを探す利用である．関数の定義箇所，APIの全利用箇所，特定ファイルの場所，ビルドターゲットに何が含まれているか，といった質問が対象だ．Code Searchはランキングとリッチなクエリー言語により，このような的を絞った質問に正確に答えられる．

検索結果のリンクはGoogle社内でコードを参照する際の正規の方法であり，バグレポート，ポストモーテム，ドキュメント内で広く使われている．古いバージョンのコードも参照可能であるため，過去の特定時点でのコードの状態を確認できる．

### 何を（What）：25%

コードベースの特定部分が何を行っているかという探索的なタスクである．これはより概念的で広いスコープの質問であり，呼び出し階層を通じた閲覧と，関連ファイル間での迅速なナビゲーション（ヘッダーファイル，実装ファイル，テストファイル，ビルドファイル間の移動）がこの種のタスクを支援する．

Code Searchのワンクリックナビゲーション機能は，この種の探索を非常に効率的にしている．開発者はシンボルをクリックしていくだけで，コードの構造と動作を理解できる．

### どのように（How）：33%

最も多い利用パターンで，他者が何かをどのように行ったかという例を見ることに関連する．特定のAPIの適用方法，特定の問題に適切なライブラリー，設計パターンの実例を探し出すために使われる．

このユースケースは，開発者が新しいAPIやライブラリーを初めて使用する際に特に重要であり，公式ドキュメントよりも実際のコード例の方が有用であることが多い．ランキングにより，最も閲覧されている（したがって最も信頼される）コード例が先に表示される．

### 何故（Why）：16%

コードが期待と異なる挙動を取る理由を探る利用で，デバッグ中に発生することが多い．コードベースの特定時点での正確な状態を検索・探索できることが重要な能力となる．このユースケースでは，バージョンコントロールとの統合が不可欠であり，変更履歴やblameビューを通じて「なぜこのコードがこのような形になったのか」を追跡できる．

### 誰が・いつ（Who/When）：8%

あるコードを誰がいつバージョンコントロールシステムに導入したかを調べる利用で，特定の行の著者や関連するコードレビューを確認できる．変更のコンテキストを理解するために，コードレビューツール（Critique）やバグトラッカーへのリンクも提供される．

<Callout type="tip" title="利用パターンの全体像">
5つの利用パターンの割合を見ると，「どのように」が33%と最大であり，これに「何を」25%，「どこに」16%，「何故」16%，「誰が・いつ」8%が続く．これは，Code Searchが単なるコード検索にとどまらず，コードの理解と学習のためのツールであることを示している．
</Callout>

## 何故独立したウェブツールなのか

Code SearchがIDEのプラグインではなく独立したウェブツールとして存在する理由には，いくつかの重要な背景がある．

### スケール

Googleのコードベースは非常に大規模であり，ローカルに全体のコピーを置くことができない．中央集権的な検索インデックスにより，インデックス構築作業は一度だけ実行すればよく，全員がその恩恵を受けられる．もし各開発者が自分のマシンでインデックスを構築しなければならないとすれば，それは計算資源の途方もない無駄遣いとなる．

ただし，相互参照用インデックスは即座には更新できず，多数のバイナリを完全にビルドまたは解析する必要があるため，1日ごとの更新となっている．テキスト検索のインデックスはほぼリアルタイムで更新されるが，セマンティックな相互参照には完全なビルドが必要となるため，トレードオフが存在する．

### 設定作業不要のグローバルコードビュー

Code Searchではプロジェクトの説明やビルド環境の設定が不要であるため，コードについて学ぶことが容易かつ高速になる．IDEの場合はプロジェクトのセットアップ，ビルド設定，プラグインの導入が必要だが，Code Searchではブラウザーを開くだけで全コードベースにアクセスできる．

この「設定作業ゼロ」の特性は，新入社員がGoogleのコードベースに素早くなじむ上で特に重要である．コードの依存関係を見落とす危険もなく，プロジェクトの境界を超えた検索も自然にできる．

### 専門化

Code SearchはIDEではないことが長所の1つである．コード編集機能を含まないことで，コードの閲覧と理解に最適化でき，全マウスクリックを意味のあるものにできる．IDEでは右クリックメニューが編集操作のための多くの選択肢を含むが，Code Searchではコード閲覧に特化した操作のみが提供される．

開発者がエディターと一緒に複数のCode Searchタブを開いておくことが極めて普通であり，コードの閲覧・理解と編集がそれぞれに最適化されたツールで行われている．

<KeyConcept title="他のツールとの統合とプラットフォーム機能">
Code Searchはソースコードを見る際の主な手段であるため，ソースコード絡みの情報を公開するプラットフォームとしても機能する．

- ログビューアーからのスタックトレースがCode Searchのソースコードへリンクされる
- クラッシュリポートツールが関連するソースコードへのリンクを提供する
- ドキュメンテーションやコードラボがCode Searchを通じてソースコードと結びつく
- コマンドラインやRPC APIを通じてプログラマティックにアクセス可能であり，自動化ツールから利用できる

Code SearchのURLは安定しており，どのドキュメントからでもコードの特定行を永続的に参照できる．このプラットフォームとしての役割は，Code Searchを単なる検索ツール以上の存在にしている．
</KeyConcept>

### API提供

Code Searchはコマンドラインインターフェイスとグーグルの標準的なRPC APIの両方を提供している．これにより，他のツールがCode Searchの検索機能を利用でき，エコシステム全体が恩恵を受けている．

## 検索インデックスの実装

Googleのコードベースは約1.5TBの内容をインデックス化しており，毎秒約200回のクエリーを処理する．サーバーサイドでの検索レイテンシーの中央値は50ミリ秒以下，インデックス化のレイテンシーの中央値は10秒以下である．

<KeyConcept title="インデックス技術の進化">
Code Searchのインデックスは以下のように進化してきた．

- **初期**：トライグラムベースのアプローチ（Russ Coxが公開したオープンソースの正規表現検索に類似）
- **中期**：カスタムな接尾辞配列ベースのソリューション
- **現在**：疎なn-gramのソリューション（ブルートフォースより500倍以上効率的）

Googleの主要な検索スタックを活用することで，逆インデックスの構築・符号化・提供における進歩から恩恵を受けている．即時的なインデックス化も標準検索スタックの機能として実現されている．

初期のトライグラムアプローチからの移行は，正規表現クエリーのパフォーマンスを大幅に改善し，特に大規模コードベースでの検索速度を劇的に向上させた．
</KeyConcept>

### ランキング

コードの検索にもウェブ検索と同様にランキングが重要である．数千件の検索結果がある場合，最も関連性の高い結果を先に表示することで，開発者の時間を節約できる．ランキングはクエリー独立シグナルとクエリー依存シグナルの2種類で構成される．

クエリー独立シグナルの代表例はファイルの閲覧数とファイルへの参照数である．参照数はPageRankアルゴリズムに類似し，各種プログラミング言語のinclude/import文をウェブのリンクの代わりに用いている．多くのファイルからインポートされているファイルは重要度が高いと判定される．

クエリー依存シグナルとしては，トークンがきれいに完全マッチする箇所へのスコア押し上げ，大文字小文字の考慮，シンボルとファイル名へのマッチのランキング内での押し上げなどがある．例えば，関数名やクラス名がクエリーと完全に一致する場合は，コメント内で一致する場合よりも高いランクが与えられる．

<Callout type="warning" title="コード検索ランキングの特殊性">
コード検索はウェブ検索と異なり，「有用な近似結果」より「正確な一致」が求められることが多い．リファクタリングのためにAPIの全利用箇所を網羅的に見つけたい場合，ランキングによって一部の結果が見落とされることがあってはならない．この要件は，通常のウェブ検索にはない固有の制約である．
</Callout>

## 選択されたトレードオフ

Code Searchの設計においては，複数のトレードオフが慎重に検討されている．

### 完全性：信頼を確保するためのインデックス化戦略

Code Searchは信頼性を重視し，インデックス化を過剰に行って失敗する方をあえて選択している．非テキストファイルはファイル名以外がインデックスから外されるが，それ以外のファイルについてはできるだけ多くの内容をインデックス化している．

この判断の背景には，開発者が信頼できない検索ツールは利用されないという経験的知見がある．検索で見つからないファイルがあると分かれば，開発者はツールを使わなくなり，代替手段（手動でのコード探索やgrepコマンド）に切り替えてしまう．信頼こそが，ツールが広く採用される上での最も重要な要素である．

### 全結果対関連結果

通常のウェブ検索は速度のために完全性を犠牲にするが，コード検索ではユースケースによって要件が異なる．コードの探索時には上位の関連結果が重要だが，リファクタリング時には全結果が必要となる．

Code Searchはこの2つの要件に対処するため，優先度で順位付けしたシャードにコードベースを分割している．通常の検索では高優先度のシャードを先に検索して高速に結果を返し，全結果検索モードでは全シャードを検索して網羅的な結果を提供する．

<Callout type="danger" title="表現力のトレードオフ">
Code Searchは正規表現検索をサポートしている．トークンベースのインデックスはスケールするが，ソースコードの多様な文字（記号，空白，演算子等）に対応できない．部分文字列インデックスは正規表現検索への拡張が容易であり，実務上は非常にうまく機能する．

完璧な正規表現インデックスは存在しないが，複雑な正規表現はクエリーのほんの一部であるため，問題となることは稀である．特に複雑な正規表現の場合，インデックスの候補フィルタリングの後にブルートフォースで正規表現をマッチさせるという手法が採られる．
</Callout>

## まとめ

Code Searchは，grepの自然な置き換えから発展し，開発者の生産性を押し上げる中心的なツールとなった．コードの理解こそがコードの開発と保守にとっての鍵であり，コードの理解への投資は実利を生み出す．

<KeyConcept title="Code Searchの核心的価値">
Code Searchの核心的価値は以下の3点に集約される．

- 開発者によるコードの理解を支援し，エンジニアリングの生産性を大きく押し上げる．最重要な2つの機能であるKythe統合と動作するサンプルコードの発見も，コードの理解に最も明快に結びついている
- 他のツールの基盤として，また全てのドキュメンテーションと開発者ツールがリンクする中心的かつ標準的な場所としての付加価値がある
- 信頼がある場合のみ広く利用されるのであり，全コードをインデックス化し全結果を返し望む結果をまず与える場合のみ信頼される．信頼は一度失うと取り戻すのが極めて困難である
</KeyConcept>
