問題解決型の文書を書く場合，考えのピラミッドを作る前に，まず問題を正しく定義し，分析を構造化する必要があります．この章では，問題定義のフレームワークを使い，導入部のS-C-Q（状況-複雑化-疑問）構造を決定するテンプレートとして活用する方法を学びます．

## 問題とは何か

問題が存在すると判断する時，通常は今までの延長線上の結果と本来望んでいた結果の間にギャップを感じています．

<KeyConcept title="問題の基本構造">
- R1（望ましくない結果）：現状のままでは生み出される結果
- R2（望ましい結果）：本来欲しいと思う結果
- 問題：R1とR2の間のギャップ
- 解決：R1からR2にどうやって到達できるかを伝えること

問題を定義するということは，「連鎖分析」プロセスの初期ステップを行うことを意味しています．
</KeyConcept>

連鎖分析では，以下の5つの質問に答えを見つけます．

1. 問題がありそうか？（あるいは改善の機会がありそうか？）
2. 問題はどこにあるのか？
3. 問題はなぜ存在するのか？
4. 問題に対し何ができるか？
5. 問題に対し何をすべきか？

質問1と2が問題定義，質問3が原因発見，質問4と5が問題解決のためのものです．

## 問題定義のフレームワーク

問題は突然降ってわいたように現れるものではありません．今までの状況の結果として発生し，特定の環境下でさまざまな影響を受けながら拡大してきたものです．

### 4つの構成要素

問題を正しく定義するためには，4つの要素を特定する必要があります．

<KeyConcept title="問題定義の4つの要素">
1. スタートポイント/オープニング：問題が発生した構造やプロセス
2. 懸念される出来事：うまく機能できなくなる何かの出来事
3. R1（望ましくない結果）：解決しようとしている問題
4. R2（望ましい結果）：構造やプロセスを使い，R1に代わって生み出したいもの

これらの要素に答えることができれば，問題は適切に定義されているといえます．
</KeyConcept>

### スタートポイント/オープニング

真っ暗な劇場の客席に腰を下ろしている姿をイメージしてみてください．ステージの幕が開き，目の前にはある時代のある瞬間，ある場所を描写するセットが広がります．これがスタートポイントです．

典型的なオープニングの例は以下の通りです．

- 構造の場合：組織図，コンピュータのシステム構成図，工場の配置図，市場分布図
- プロセスの場合：販売活動，情報システム，事務管理プロセス，流通システム，製造プロセス

### 懸念される出来事

「懸念される出来事」とは，構造やプロセスがうまく機能できなくなる出来事を指します．以下の3つの形を取ります．

<Callout type="note" title="懸念される出来事の3つの形態">
- 外的引き金：環境から引き起こされる変化（新たな競合の出現，技術の転換，政府方針の変化など）
- 内的引き金：会社自身により引き起こされる変化（新システムの導入，新市場への進出など）
- 新たな認識：変化が必要なことへの新たな認識（能力低下，水準以下の結果など）
</Callout>

### R1とR2の定義

R1とは読み手が解決しようとしている問題であり，R2とは構造やプロセスを使って生み出したいものです．R2はできる限り具体的に，かつ数値で述べるべきです．なぜなら，将来の時点でそれが実現できたかどうかを明確に判断したいからです．

## 導入句へ変換する

解決策を文書にする準備が整えば，問題の定義を導入部に変換するのは楽な作業です．並べたものを単純に左から右へと読んでいけばよいのです．

- S（状況）= スタートポイント/オープニング + 懸念される出来事
- C（複雑化）= 読み手が今現在知っている最新の情報
- Q（疑問）= R1からR2へ到達するための質問

## 7つの問題状況

読み手が直面する問題状況は，問題追究のどのステージにいるかによって，7つのパターンに分類できます．

<KeyConcept title="7つの問題状況パターン">
最も一般的な状況：
1. R1からR2へ移行する方法を知らない → Q：どうすべきか？
2. 移行方法をわかっているつもりだが，確信がない → Q：それは正しいか？
3. 移行方法をわかっているが，実行方法がわからない → Q：どのように実行するか？

一般的状況の変形：
4. 解決案を実行したが，うまくいかなかった → Q：何をすべきか？
5. いくつかの解決案があるが，どれを選ぶべきかわからない → Q：どの選択肢がベストか？

一般的ではないがあり得る形：
6. R1はわかっているが，R2を明確にできない → Q：戦略はどうあるべきか？
7. R2はわかっているが，R1かどうかがはっきりしない → Q：問題があるのか？
</KeyConcept>

## 導入部へ展開する

各問題状況に応じた導入部の展開パターンを見てみましょう．

### パターン1：我々は何をすべきか？

これは最も簡単な構造です．状況は常に今起きていることを記述し，複雑化では読み手が今R1にいてR2に行くことを望んでいることを述べます．

- S：これが現在稼働しているシステムです
- C：本来意図しているようには稼働していません
- Q：どのようにして，本来意図しているように稼働させるか？

### パターン5：どの選択肢を選ぶべきか？

選択肢は常に，導入句の「複雑化」の部分に登場します．

<Callout type="warning" title="選択肢提示の注意点">
単に分析のためにのみ選択肢を持ち出してはいけません．「X方式はよくない，Y方式はよくない，したがってZ方式を行え」ではなく，Zを行う理由はZが問題を解決するからです．
</Callout>

### パターン6：我々の戦略はいかなるものであるべきか？

状況があまりにも新しいか，知識が乏しいために具体的な目的や行動ステップを判断できない場合に使います．コンサルタントが業界分析を依頼され，成功要因を把握し，顧客の強みを前提として効果的な競争戦略を決定するような場合です．

## 実際の例

問題定義から最後のピラミッド作りまでの実例として，家庭用品の小売チェーンの物流問題を見てみましょう．

会社は3つの物流センターを保有しており，さらに倉庫スペースを賃借していました．年間成長率4-5%と5年以内に198店舗を出店する計画を考慮すると，2年以内に配送能力が満杯に達することが確実でした．

<Callout type="tip" title="問題定義から導入部への変換">
S = 490店舗に対応するはずの3つの倉庫は，現実には賃貸スペースを用いた上で438店舗分にしか対応していない．さまざまな拡充方法がある．

C = いつ何を行うかによって投資収益率に対するインパクトは異なる．投資額と操業コストが最も低いオプションを選択したい．

Q = 物流戦略はどうあるべきか？
</Callout>

このように問題定義のフレームワークを使えば，取り立てた苦労もなしに，問題を簡潔な導入部に置き換えることができます．コツは，左から右そして下部へと読み進み，読み手が知る最新の情報を「複雑化」とすることです．
